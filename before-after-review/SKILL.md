# Before / After Review

Review existing UI changes independently of how they were proposed. No scored reviews or design-grind session is required.

1. Establish and pin the original baseline from the user's screenshots, revisions, or starting work, including local changes. Reuse the supplied baseline when continuing a review; for design-grind it is the state at the start of the grind. Keep `revision.base`, Before descriptions, and original captures fixed across all rounds, including after applying decisions. Only `revision.head` and revised After proposals advance. Save baseline captures separately; recreate newly needed states from the pinned original snapshot, never an intermediate iteration. Disclose unavailable original evidence instead of substituting a later state.
2. Capture matching before/after states at the same viewport, language, and relevant application state. Cover affected loading, empty, error, success, disabled, expanded, dialog, and keyboard states where meaningful. Use genuine captures; describe missing evidence instead of inventing it.
3. Maintain a cumulative catalog with stable board and change IDs. Each independent accept/decline decision has a brief reason and before/after descriptions. Keep unchanged reviewed entries and their evidence intact so prior choices remain valid; update affected entries and add new IDs for new decisions. Disclose coupled changes or screenshot limitations in `context`; use captured stages for multiple views of the same decision, always against the original Before state.
4. Build the bundled [decision board](references/board.md) from the catalog and screenshots. On rebuilds, supply the latest exported JSON with `--decisions` so previous choices and notes travel with the HTML, including in a fresh browser or embed. Verify unchanged accepted items stay accepted and only changed or new items need review. Keep the viewer unchanged across tasks, and keep product assets and source decision records outside this skill.
5. Present the board for review. Accept / Decline and notes are independent. If no exported decisions were supplied, leave the board and catalog available for the user to review and export; do not invent selections.
6. Read the exported JSON and match its board ID, revision, change IDs, and fingerprints to the reviewed catalog. Retain accepted changes, undo only the proposed changes that were declined, and leave pending changes undecided. Use notes to revise proposals without treating a note as acceptance. Verify the selected combination, then rebuild with the same original baseline, cumulative catalog, and exported decisions. Unchanged choices carry forward; changed evidence preserves the previous choice and note while requesting a fresh decision. Do not relabel an intermediate proposal as Before or mark a revised proposal accepted on the user's behalf.
